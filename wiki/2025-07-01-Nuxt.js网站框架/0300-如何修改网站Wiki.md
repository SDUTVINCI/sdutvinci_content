Vinci 机器人队网站的 Wiki 有三种编辑方式：CMS 富文本编辑、CMS 在线 Markdown 编辑，以及通过 GitHub Pull Request（下文简称 PR）提交修改。

如果只是修改少量文字，前两种方式更直接；如果需要新增章节、批量修改、使用本地编辑器或保留完整的代码审查记录，推荐使用第三种方式。

## 方式一：使用 CMS 富文本编辑器

1. 打开 [CMS 登录页](/cms/login)，登录已通过审核的成员账号。
2. 在“文章”中找到需要修改的 Wiki，创建编辑草稿；也可以在“草稿”页面新建文章草稿。
3. 在编辑页选择“富文本”，像使用普通文档编辑器一样修改标题、段落、列表、图片和代码块。
4. 保存前查看“发布效果”，确认排版正确。

富文本适合不熟悉 Markdown 的成员。如果页面含有 HTML、Vue/MDC 组件或其他扩展语法，编辑器可能显示兼容性警告；此时应使用 Markdown 源码模式并仔细核对预览。

## 方式二：在 CMS 中直接编辑 Markdown

1. 按照方式一进入文章草稿。
2. 选择“Markdown 源码与预览”。
3. 在左侧直接修改 Markdown，在右侧对照网站最终的发布效果。
4. 需要图片时，可使用草稿页面的图片上传功能，系统会上传图片并插入对应的 Markdown 链接。

这种方式无需在本地安装 Git，适合单篇文章的精确修改。

## 方式三：通过 GitHub PR 导入（推荐）

### 为什么推荐 PR

PR 适合较大的 Wiki 修改，也适合熟悉 VS Code 和 Git 的成员：

- 可以在本地使用 VS Code 的搜索、预览、格式化和图片上传工具。
- 可以一次修改多篇文章，并在 GitHub 中清楚查看每一行差异。
- 修改人和审核人可以在 PR 中讨论，不会直接改动正式网站。
- CMS 导入时会检查路径、Frontmatter、内容冲突和高风险语法。

### 第一步：准备内容仓库和分支

网站的 Markdown 位于 [`SDUTVINCI/sdutvinci_content`](https://github.com/SDUTVINCI/sdutvinci_content) 内容仓库。先从最新的 `main` 创建自己的分支，不要直接在 `main` 上修改。

Wiki 的常见路径如下：

```text
wiki/
└── 2025-07-01-Nuxt.js网站框架/
    ├── index.md
    ├── 0100-简介.md
    ├── 0200-部署方案.md
    └── 0300-如何修改网站Wiki.md
```

- 最外层 Wiki 目录使用 `YYYY-MM-DD-专题名` 的格式。
- `index.md` 是该专题的入口页。
- 普通章节用 `0100-`、`0200-`、`0300-` 等前缀排序，通常每次递增 `100`，便于以后插入章节。
- 不要手工修改 `.vinci/snapshot.json`；它由网站内容导出流程维护。

### 第二步：编辑 Markdown 和 Frontmatter

修改已有文章时，保留文件原有的 `vinciId`，不要删除、更换或复制给其他文章。

通过 PR 新增文章时，则不要手工填写 `vinciId`、`publishedAt` 和 `updatedAt`。CMS 导入和正式发布时会分别生成稳定 ID 和时间信息。新文章可以从下面的 Frontmatter 开始：

```yaml
---
title: 文章标题
description: 用一句话介绍这篇文章
authors:
  - zhangsan
---
```

`authors` 使用成员的稳定拼音 ID，不要直接填中文姓名。网页会根据稳定 ID 显示成员中文姓名；如果不确定自己的 ID，可以在 CMS 的成员或文章署名信息中查询。

对文章做实质性补充但不是原作者时，可在 Frontmatter 中增加 `contributors`：

```yaml
contributors:
  - lisi
```

提交前至少检查：

- Markdown 预览是否正常，标题层级是否连续。
- 图片是否使用可访问的 CDN HTTPS 链接，且 alt 文本能说明图片内容。
- 文件是否仍位于正确的 Wiki 目录，有没有意外改动其他文章。
- 已有文章的 `vinciId` 是否保持不变，新文章是否没有手工填写 `vinciId`。

### 第三步：创建 GitHub PR

1. 将分支 Push 到 GitHub。
2. 创建一个目标为 `SDUTVINCI/sdutvinci_content` 的 `main` 分支的 PR。
3. 在 PR 标题和说明中写清修改了哪些 Wiki、修改原因和需要重点检查的地方。
4. 在 `Files changed` 中查看完整差异，确认没有 Token、密码、本机绝对路径或无关文件。

PR 是内容提案入口，不是网站的正式发布入口。不要为了让网站更新而手工 Merge PR；正式内容由 PostgreSQL 管理，管理员发布后，系统会再把正式版本导出回内容仓库。

### 第四步：在 CMS 导入 PR

1. 登录 CMS，打开[“外部内容导入”](/cms/content-imports)。
2. 输入 PR 链接或 PR 编号，让系统先执行 Dry Run 检查。
3. 根据页面显示查看每一项的类型、风险、冲突和阻止原因。转移、删除、高风险语法和内容冲突需要额外确认或处理。
4. 选择需要导入的可操作项目，再执行导入。

导入只会创建 PostgreSQL 草稿或提案，不会自动 Merge PR、通过审核或发布网站。页面显示“已创建草稿”后，还需要继续完成下一节的审核流程。

导入完成后，维护者可以把检查摘要留言到 PR。管理员确认所需项目均已安全导入后，可以关闭 PR；如果源分支位于官方内容仓库，还可以在 PR 关闭后单独确认删除源分支。

## 草稿导入后：提交审核和正式发布

无论使用上面哪种编辑方式，内容都不会在保存或 PR 导入后立刻出现在正式网站上。完整流程是：

```text
创建或导入草稿
        ↓
编辑者检查预览并提交审核
        ↓
管理员审核（通过或驳回）
        ↓
管理员正式发布
        ↓
前台网站更新，正式 Markdown 随后导出到内容仓库
```

1. 进入 CMS 的“草稿”页，打开刚创建或导入的草稿。
2. 检查标题、摘要、作者、协作者、Wiki 路径、正文和“发布效果”。
3. 点击“提交审核”。审核完成前，提交人可以按页面提示撤回。
4. 管理员在“审核”页查看变更内容和预览，选择审核通过或驳回。
5. 审核通过不等于已经上线；管理员还需要对“待发布”文章执行“正式发布”。

如果审核驳回，编辑者应根据意见修改原草稿，再次检查预览并重新提交。只有“正式发布”成功后，这次 Wiki 修改才会成为网站的正式内容。

## 常见问题

### PR 已经创建，为什么网站还没变？

PR 只是提案。请确认已在 CMS 中完成 PR 导入，导入的草稿已提交审核，且管理员已经审核通过并正式发布。

### 为什么某个文件被阻止导入？

先阅读页面显示的具体阻止原因。常见原因包括路径或 Frontmatter 无效、已有活动草稿、数据库正式版本与 PR Base 冲突，以及新增了 HTML、Vue/MDC 等高风险语法。不要通过删除 `vinciId`、强行覆盖或手工修改 snapshot 规避检查。

### 导入后还可以在 CMS 里继续修改吗？

可以。PR 导入后生成的是普通 CMS 草稿，可以继续使用富文本或 Markdown 源码模式修改。修改后仍需保存、核对发布效果并提交审核。
