这一章先不改代码，只做一件很具体的事：

在 Windows 上把我准备好的 CMake 模板跑起来。

我们继续使用 GCC、CMake、Ninja 和 VSCode。准备好环境后，后面的 C++ 代码和 Linux 章节共用，不需要再学一套语法。
如果你用的是 Linux，请看 [Linux开发环境搭建与测试](/wiki/2023-10-05-cplusplus-jiao-xue/0100-0100-linux-kai-fa-huan-jing-da-jian-yu-ce-shi)。

## 本章最终效果

这一章会按下面的顺序来：

1. 安装 MSYS2，用它准备 GCC、CMake、Ninja、GDB 和 Eigen。
2. 配置 Windows 的 PATH，检查这些工具能否正常运行。
3. 下载模板，选择 `windows-debug`，先原样运行。
4. 用 VSCode 构建、运行和调试模板程序。
5. 确认以后在哪里写代码、在哪里重新构建。

本节按 Windows 10 / 11 的 64 位环境讲解。
工具的安装窗口和版本号可能会变化，重点看工具名称、安装路径和命令输出。

## 为何采用 MSYS2

在 Windows 上分别下载、解压和配置开发工具，需要处理多个安装目录和环境变量。MSYS2 可以通过包管理器统一安装和更新工具，提供接近 Linux 的配置体验，因此本教程采用 MSYS2 UCRT64。

## 先认识 MSYS2 和 UCRT64

MSYS2 是 Windows 上的一套开发工具和软件包管理环境。
我们用它安装编译器和依赖，类似 Linux 用 `apt` 或 `dnf` 安装软件。

UCRT64 是 MSYS2 提供的一种环境，使用 GCC，面向 64 位 Windows，并采用微软的 UCRT。这里统一选择它，安装的软件包也都使用 `mingw-w64-ucrt-x86_64-` 前缀。

| 名字 | 本章里负责什么 |
|:---|:---|
| MSYS2 | 安装、更新开发工具和库 |
| UCRT64 | 本章使用的 64 位 Windows GCC 环境 |
| `pacman` | MSYS2 的软件包管理命令 |
| `gcc` / `g++` | 编译 C / C++ 代码 |
| CMake / Ninja | 配置工程、执行构建 |
| GDB | 下断点、查看变量、单步运行 |

这些工具生成的是原生 Windows 可执行程序。模板本身没有写死 MSYS2 路径，也可以使用独立安装的 MinGW-w64 工具链。

环境区别见 [MSYS2 官方说明](https://www.msys2.org/docs/environments/)，VSCode 的 [Windows GCC 教程](https://code.visualstudio.com/docs/cpp/config-mingw)也使用这条安装路线。

## 使用已经单独安装好的工具

> **对于你的电脑可能曾经安装过GCC，G++，CMake，Ninja，GDB，Eigen才需要看！新人请跳过**

如果电脑上已经有支持 C++20 的 MinGW-w64 GCC、CMake 3.22+、Ninja 和 GDB，也可以继续使用，不必更换安装方式。

把它们各自的 `bin/` 加入 PATH，再按前面的版本检查、configure 和 build 步骤执行即可。

Eigen 是头文件库，不需要分别编译 GCC 版和 MSVC 版。
对于当前模板的 `find_package(Eigen3 REQUIRED)`，还需要安装目录提供 `Eigen3Config.cmake`。

例如 Eigen 安装在 `C:/deps/eigen`，可以临时设置安装前缀：

```powershell
$env:CMAKE_PREFIX_PATH = "C:/deps/eigen"
cmake --preset windows-debug
```

或者直接指定配置文件所在的目录：

```powershell
cmake --preset windows-debug -DEigen3_DIR="C:/deps/eigen/share/eigen3/cmake"
```

上面的路径要对应实际文件位置。单纯解压 Eigen 源码可以获得头文件，但不一定已经有生成好的 CMake 配置文件；使用安装包或先执行 Eigen 的 CMake 安装步骤，更适合当前模板的查找方式。参见 [Eigen 官方 CMake 说明](https://libeigen.gitlab.io/eigen/docs-nightly/TopicCMakeGuide.html)。

## 常见问题

### 找不到 gcc、Ninja 或 GDB

先检查对应的软件包是否装好，再用 `where.exe` 检查 PATH。修改系统环境变量后，需要重新打开 VSCode，它不会自动获得已经打开之后才修改的 PATH。

### 看不到 windows-debug

确认打开的是项目根目录，里面包含 `CMakePresets.json`。模板按当前系统显示 configure preset；Windows 使用 Windows 原生 CMake 执行时，应看到 Windows 两组预设。

### 程序启动失败

先确认运行的是 `build/windows-debug/bin/cmake_template.exe`，并且开发环境的 GCC 工具目录位于 PATH 中。

测试安装结果时，重新执行 install，再运行安装目录中的 EXE，不要只把 EXE 从目录中单独拿出来。

### 切换编译器后构建异常

一个构建目录会缓存之前选择的编译器。更换工具链后，在 PowerShell 中清理对应的构建目录，再重新配置：

```powershell
Remove-Item -Recurse -Force build/windows-debug
cmake --preset windows-debug
cmake --build --preset windows-debug
```

只有目录存在时才执行删除命令，删除前确认路径是项目的构建目录。这里不要求使用 `cmake --fresh`，这样也兼容模板最低要求的 CMake 3.22。

### 中文显示乱码

先将源文件保存为 UTF-8，并使用支持 UTF-8 的终端。
PowerShell 终端中的编码设置与源文件编码是两件事；
需要时可以在当前终端执行 `chcp 65001` 后重新运行。
涉及文件内容时，文件本身的编码也要一致。
